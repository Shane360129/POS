## 1. 設計原則

### 1.1 Schema 隔離（模組邊界即資料邊界）

同一個資料庫內，以 **schema 作為模組邊界**。每個核心模組獨佔一個 schema：

| schema | 模組 | Phase | 職責摘要 |
| --- | --- | --- | --- |
| `iam` | Identity & Access | 1 | 使用者、角色、權限、組織單位、公司、Keycloak 對應 |
| `mdm` | Master Data & Config | 0–1 | 編號規則、幣別、匯率、稅碼、行事曆、共用代碼、**客戶/供應商主檔** |
| `inv` | 物料與庫存 | 2 | 料件、分類、單位、BOM、**多倉庫存餘額/成本**、異動、批號/序號、盤點 |
| `procure` | Procurement (P2P) | 2 | 請購、採購單、進貨驗收（含進項稅）、供應商發票 |
| `sales` | Sales / Order (O2C) | 2 | 報價、訂單、出貨、**退貨/折讓**、CRM 基本（聯絡、商機） |
| `fin` | Finance / Accounting | 3 | 科目、分錄、AR、AP、收付款、**會計期間**、**維度**、發票/字軌 |
| `audit` | Audit & Activity | 1 | 稽核軌跡（who/when/what/before/after） |
| `wf` | Workflow / Approval | 2（精簡） | 簽核流程實例與步驟（先支撐硬編碼兩階） |
| `app` | 共用基礎 | 0 | **Outbox**（跨模組事件，先建預留拆分） |

**鐵則（對齊 ADR-02）**：
1. **禁止跨模組直接 JOIN**：查詢不得 `JOIN` 到他人 schema 的核心表。
2. **禁止跨模組 FK 到他人核心表**：跨模組關聯一律以「**弱參考**」（存對方的鍵值 + 必要快照欄位），不建實體外鍵；由應用層 / in-process 介面維持一致性。
3. **本模組內部**可正常使用 FK、JOIN、cascade。
4. 跨模組讀取走 in-process 介面（`IInventoryService`…）；跨模組事件走 `app.Outbox`。

> **拆分縫**：因為跨模組沒有實體 FK、沒有 JOIN，未來把某 schema 搬到獨立資料庫時，**不會有外鍵需要拆、沒有跨庫 JOIN 需要改寫**——只需把 in-process 介面換成遠端代理、把 Outbox 消費端換成 RabbitMQ。

#### 跨模組「弱參考」範例

`fin` 的分錄需要記錄「這筆分錄屬於哪間公司、對應哪張來源單據」。它**不**建 FK 到 `sales.SalesOrder`，而是：

```
fin.JournalEntry.SourceModule = 'sales'      -- 來源模組
fin.JournalEntry.SourceType   = 'SalesOrder' -- 來源單據型別
fin.JournalEntry.SourceId     = 12345        -- 來源單據 Id（無 FK）
```

`CompanyId` 雖然語意上屬 `iam.Company`，但因為它是**橫切所有模組**的租戶鍵，視為「平台級共用維度」：各表都帶 `CompanyId`，但**僅 `iam` 內的表對 `iam.Company` 建 FK**，其餘模組以弱參考處理（保留拆分縫）。

### 1.2 命名規範

| 對象 | 規範 | 範例 |
| --- | --- | --- |
| Schema | 小寫模組代號 | `inv`、`fin` |
| Table | 單數、PascalCase | `inv.Product`、`fin.JournalEntry` |
| 欄位 | PascalCase | `UnitCost`、`CompanyId` |
| 主鍵 | `Id`（`bigint`，見 §1.4） | `Id` |
| 外鍵欄位 | `<關聯實體>Id` | `ProductId`、`WarehouseId` |
| 唯一鍵索引 | `UX_<Table>_<欄位...>` | `UX_Product_Company_Code` |
| 一般索引 | `IX_<Table>_<欄位...>` | `IX_StockMovement_Product_Wh_Date` |
| CHECK 約束 | `CK_<Table>_<規則>` | `CK_JournalLine_DebitCredit` |
| 外鍵約束 | `FK_<子表>_<父表>` | `FK_JournalLine_JournalEntry` |
| 列舉欄位 | 存 `tinyint`/`smallint`（含註解對照）或 `varchar` 代碼 | 見各表 |

> **大小寫可移植性**：PostgreSQL 對未加引號識別字會轉小寫。EF Core 產生 DDL 時會統一加引號，故 PascalCase 可保留；但若有人手寫 SQL，PostgreSQL 端需用 `"PascalCase"`。本文件 DDL 以 SQL Server 為主體並標註 PG 差異。

### 1.3 可移植性原則（SQL Server ↔ PostgreSQL）

設計避免供應商鎖定；必要處以對照表處理差異：

| 主題 | SQL Server | PostgreSQL | 設計策略 |
| --- | --- | --- | --- |
| 主鍵自增 | `bigint IDENTITY` | `bigint GENERATED ... AS IDENTITY` | 邏輯一致，EF 產生 |
| 樂觀鎖版本 | `rowversion`（8-byte 自動） | `xmin`(系統欄) 或 `bytea`/`bigint` 手動遞增 | 見 §2.4，抽象為 `RowVersion` |
| 序列號 | `CREATE SEQUENCE` | `CREATE SEQUENCE` | **兩者皆原生支援**（編號改用 sequence 的關鍵理由） |
| GUID | `uniqueidentifier` | `uuid` | 用於 `Outbox.EventId` 等冪等鍵 |
| 金額 | `decimal(18,4)` | `numeric(18,4)` | 語意相同 |
| 時間戳 | `datetime2` | `timestamptz` | 一律存 **UTC**；應用層轉時區 |
| 布林 | `bit` | `boolean` | EF 對應 |
| JSON | `nvarchar(max)`（+ `ISJSON`/`JSON_VALUE`） | `jsonb` | `Outbox.Payload`、`AuditLog.Before/After` |
| 觸發器語法 | `CREATE TRIGGER ... AS` | `CREATE TRIGGER ... EXECUTE FUNCTION` | 借貸 CHECK 的觸發器版本兩邊各給（§4） |
| 字串型別 | `nvarchar`（Unicode） | `varchar`/`text`（預設 UTF-8） | 中文：SQL Server 必須 `nvarchar` |

**通用規則**：
- 不用 SQL Server 專有的 `MONEY`、`SMALLDATETIME`、`TEXT`/`NTEXT`（已棄用）。
- 不在 schema 物件名硬編資料庫名（不用 `[db].[schema].[table]` 三段式）。
- 業務邏輯盡量放應用層；DB 端只放「跨入口都必須成立的硬約束」（借貸平衡、唯一鍵、期間鎖、權限收斂）。

### 1.4 共用欄位（每張業務表必備）

除了純關聯表（如 `RolePermission`）與系統表，**每張主檔/交易表都包含**以下共用欄位（對齊檢核 §12.1 與本文件需求 #2）：

| 欄位 | 型別（SQL Server / PG） | 必填 | 說明 |
| --- | --- | --- | --- |
| `Id` | `bigint IDENTITY` / `bigint GENERATED AS IDENTITY` | PK | 代理主鍵。用 `bigint` 預留量體（取代現況 `int`）。 |
| `CompanyId` | `bigint` | ✅ | **多公司橫切租戶鍵**。全域 query filter 依此過濾（§9）。 |
| `CreatedBy` | `bigint`（→ `iam.User.Id`，弱參考） | ✅ | 建立者使用者 Id。 |
| `CreatedAt` | `datetime2` / `timestamptz` | ✅ | 建立時間（UTC）。 |
| `UpdatedBy` | `bigint` | ✕（首建為 null） | 最後修改者。 |
| `UpdatedAt` | `datetime2` / `timestamptz` | ✕ | 最後修改時間（UTC）。 |
| `RowVersion` | `rowversion` / `bytea`（見下） | ✅ | **樂觀鎖**。EF `[Timestamp]`/`IsRowVersion()`。 |

**`RowVersion` 可移植性**：
- SQL Server：用原生 `rowversion`（自動遞增，零維護）。
- PostgreSQL：以 `xmin` 系統欄做並行權杖（EF Npgsql 支援 `UseXminAsConcurrencyToken()`），或自管 `bigint Version` 由 `UPDATE` 時 `+1`。設計上抽象為「`RowVersion` 概念」，由 ORM provider 各自實作。

> **append-only 表例外**：`fin.JournalEntry`/`fin.JournalLine`、`audit.AuditLog`、`inv.StockMovement`、`app.Outbox` 為**不可變/只追加**表，**不含 `UpdatedBy/UpdatedAt/RowVersion`**（它們本來就不該被更新）。

### 1.5 列舉（Enum）儲存策略

採「**`tinyint`/`smallint` + 文件對照**」為主（省空間、索引快），關鍵狀態欄位額外加 `CHECK` 限制合法值，避免寫入越界。範例見 `fin.AccountingPeriod.Status`、`DocStatus`。

## 2. 共用與平台層資料表

### 2.1 `app.Outbox`（跨模組事件，單體階段即先建）

即使單體階段分錄走本地同交易（ADR-03），仍**先建 Outbox**，為日後拆分預留（對齊檢核 §12.1、總計畫技術選型）。寫入 Outbox 與業務變更在**同一交易**內完成（交易性 Outbox 模式）。

| 欄位 | 型別 | 鍵/約束 | 說明 |
| --- | --- | --- | --- |
| `Id` | `bigint IDENTITY` | PK | 流水序，保證消費順序基準。 |
| `EventId` | `uniqueidentifier`/`uuid` | **UNIQUE** | **冪等鍵**：消費端以此去重（at-least-once 投遞防重）。 |
| `CompanyId` | `bigint` | NOT NULL | 租戶。 |
| `AggregateType` | `varchar(100)` | NOT NULL | 聚合根型別，如 `SalesOrder`。 |
| `AggregateId` | `bigint` | NOT NULL | 聚合根 Id。 |
| `Type` | `varchar(150)` | NOT NULL | 事件型別，如 `sales.OrderShipped`。 |
| `Payload` | `nvarchar(max)`/`jsonb` | NOT NULL | 事件內容（JSON）。 |
| `OccurredAt` | `datetime2`/`timestamptz` | NOT NULL | 事件發生時間（UTC）。 |
| `ProcessedAt` | `datetime2`/`timestamptz` NULL | — | 已投遞/已消費時間；NULL = 待處理。 |
| `Attempts` | `int` | DEFAULT 0 | 投遞嘗試次數（dead-letter 判斷）。 |
| `Error` | `nvarchar(max)` NULL | — | 最後一次失敗訊息。 |

索引：
- `UX_Outbox_EventId`（UNIQUE）— 冪等。
- `IX_Outbox_Unprocessed` ON `(ProcessedAt) WHERE ProcessedAt IS NULL`（**篩選索引**；PG 用 partial index）— 背景派送器只掃未處理列。

DDL 見 §7.6。

### 2.2 共用「狀態」與「單據型別」約定

- `DocStatus`（`tinyint`）：`0=Draft 草稿`、`1=Confirmed 已確認/已過帳`、`2=Cancelled 作廢`、`3=Closed 已結案`。各交易表沿用，並以 `CHECK` 限制。
- 跨模組來源追溯統一三欄：`SourceModule`(varchar20)、`SourceType`(varchar50)、`SourceId`(bigint)。

### 3.2 `mdm` — 主檔與設定

#### `mdm.NumberSequence`（編號規則，取代 `Count()+1`）★
> **修正既有 bug**（檢核 §4、ADR-09）。現況 `NextNumberAsync` 用 `Count()+1`，併發/作廢會重號。改為**每個（公司, 單據類別, 期間桶）一個 DB sequence / Hi-Lo 配置**。

兩種落地，本表存「規則與當前值」，實際取號方式擇一（見下）：

| 欄位 | 型別 | 鍵/約束 | 說明 |
| --- | --- | --- | --- |
| `Id` | bigint | PK | |
| `CompanyId` | bigint | NOT NULL | 租戶。 |
| `DocType` | varchar(20) | | 單據類別：`PO/SO/JE/INV/SR/CN/GR/PR`… |
| `Prefix` | varchar(10) | | 字軌前綴。 |
| `PeriodBucket` | varchar(8) | | 重置粒度：`yyyy`/`yyyyMM`/空(永不重置)。 |
| `CurrentValue` | bigint | NOT NULL DEFAULT 0 | Hi-Lo 模式下的「目前高位」；DB sequence 模式僅作備援。 |
| `IncrementBy` | int | DEFAULT 1 | Hi-Lo 區段大小（如 50）。 |
| `Pad` | int | DEFAULT 4 | 流水號補零位數。 |

唯一鍵：`UX_NumberSequence (CompanyId,DocType,PeriodBucket)`。

**取號實作（兩擇一，皆可移植）**：
1. **DB SEQUENCE（首選）**：對每個字軌建原生 `SEQUENCE`（SQL Server 與 PostgreSQL **都原生支援**），由 `NEXT VALUE FOR`/`nextval()` 原子取號，無鎖競爭、不受作廢影響。期間重置以「sequence 名含期間」或定期重建處理。
2. **Hi-Lo**：應用啟動時對 `CurrentValue` 做 `UPDATE ... SET CurrentValue = CurrentValue + IncrementBy OUTPUT`（單一原子語句），取得一段區間在記憶體內分配，降低 DB round-trip。EF Core 內建 `UseHiLo()`。

> 兩者都**保證不重號**（不再依賴 `Count`），且**作廢不影響後續號碼**。

## 4. 分錄硬約束（借貸平衡，append-only）

> 落實 ADR-08、Must-fix #3、檢核 §1.2/§12.1。目標：**任何寫入路徑都無法產生不平衡或可竄改的分錄**。採「應用層 + DB 雙保險」。

### 4.1 三道防線

| 層級 | 機制 | 防的事 |
| --- | --- | --- |
| **應用層** | `AccountingService` 在**顯式交易**（`BeginTransaction`）內建立分錄；建立前驗證 Σ借=Σ貸；本身計算 `TotalDebit/TotalCredit`。 | 邏輯錯誤、現況「兩次 SaveChanges 無交易」的 bug（補上單一交易）。 |
| **DB 行級 CHECK** | `CK_JournalLine_DebitCredit`：一行不得同時有借與貸、不得為負。`CK_JournalEntry_Balanced`：單頭 `TotalDebit=TotalCredit`。 | 一行金額方向錯誤；單頭合計不平。**任何入口（含手寫 SQL）都擋。** |
| **DB 觸發器** | `TR_JournalLine_Balance`：在 line 異動後，重算該 entry 的 `Σ(Debit)` 與 `Σ(Credit)`，若不等則 `ROLLBACK`/`RAISE`。**保證 line 合計與單頭一致**（防止只塞單邊行）。 | 繞過 service、CHECK 無法跨列驗證的漏洞（CHECK 是行級，跨列加總需觸發器）。 |

> **為何單頭也存合計並加 CHECK**：行級 CHECK 無法「跨列加總比較」；把 `TotalDebit/TotalCredit` 冗餘存在單頭並加 `CHECK(TotalDebit=TotalCredit)`，搭配觸發器確保「單頭合計 = 明細加總」，即可在**不掃全表**的情況下保證平衡，且試算表可直接 `SUM` 單頭欄位快速比對。

### 4.2 append-only（不可竄改）

- `fin.JournalEntry`/`fin.JournalLine` 與 `audit.AuditLog`、`inv.StockMovement`：**應用程式使用的 DB 帳號只授予 `SELECT`/`INSERT`，不授予 `UPDATE`/`DELETE`**（§8）。
- 更正一律走**沖銷分錄**：產生 `IsReversal=1` 且 `ReversedEntryId` 指向原分錄的反向分錄（借貸對調），再開正確分錄。取代現況 `ReverseJournalAsync` 只抓「第一筆」的脆弱做法——改以明確的 `ReversedEntryId` 一對一對應。
- 沖銷分錄本身也須通過期間檢查（不能往已關期間沖）。

### 4.3 期間鎖定觸發器（與分錄寫入綁定）

`TR_JournalEntry_PeriodCheck`：INSERT 分錄時，依 `EntryDate` 找對應 `fin.AccountingPeriod`，若該期 `Status<>0`（非 Open）則拒絕寫入。應用層先做友善檢查，DB 觸發器作最後防線。

### 4.4 SQL 範例

**行級 CHECK（SQL Server / PostgreSQL 通用）**：
```sql
-- fin.JournalLine：一行只能借或貸，且非負
ALTER TABLE fin.JournalLine
  ADD CONSTRAINT CK_JournalLine_DebitCredit
  CHECK ( (Debit = 0 OR Credit = 0) AND Debit >= 0 AND Credit >= 0 );

-- fin.JournalEntry：單頭借貸合計相等
ALTER TABLE fin.JournalEntry
  ADD CONSTRAINT CK_JournalEntry_Balanced
  CHECK ( TotalDebit = TotalCredit );
```

**跨列平衡觸發器 — SQL Server**：
```sql
CREATE TRIGGER fin.TR_JournalLine_Balance
ON fin.JournalLine
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;
    -- 受影響的分錄單頭
    IF EXISTS (
        SELECT je.Id
        FROM fin.JournalEntry je
        JOIN fin.JournalLine jl ON jl.JournalEntryId = je.Id
        WHERE je.Id IN (
            SELECT JournalEntryId FROM inserted
            UNION SELECT JournalEntryId FROM deleted
        )
        GROUP BY je.Id, je.TotalDebit, je.TotalCredit
        HAVING SUM(jl.Debit) <> SUM(jl.Credit)          -- 明細借≠貸
            OR SUM(jl.Debit) <> MAX(je.TotalDebit)       -- 明細借≠單頭借合計
            OR SUM(jl.Credit) <> MAX(je.TotalCredit)     -- 明細貸≠單頭貸合計
    )
    BEGIN
        RAISERROR('分錄借貸不平衡或與單頭合計不符，交易已回滾。', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

**跨列平衡觸發器 — PostgreSQL**（語法差異）：
```sql
CREATE OR REPLACE FUNCTION fin.fn_journalline_balance()
RETURNS trigger AS $$
DECLARE bad int;
BEGIN
    SELECT count(*) INTO bad
    FROM fin."JournalEntry" je
    JOIN fin."JournalLine" jl ON jl."JournalEntryId" = je."Id"
    WHERE je."Id" IN (COALESCE(NEW."JournalEntryId", OLD."JournalEntryId"))
    GROUP BY je."Id", je."TotalDebit", je."TotalCredit"
    HAVING sum(jl."Debit") <> sum(jl."Credit")
        OR sum(jl."Debit") <> max(je."TotalDebit")
        OR sum(jl."Credit") <> max(je."TotalCredit");
    IF bad > 0 THEN
        RAISE EXCEPTION '分錄借貸不平衡或與單頭合計不符';
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE CONSTRAINT TRIGGER TR_JournalLine_Balance
AFTER INSERT OR UPDATE OR DELETE ON fin."JournalLine"
DEFERRABLE INITIALLY DEFERRED          -- 延後到交易結束才檢查，允許先插單頭再插多行
FOR EACH ROW EXECUTE FUNCTION fin.fn_journalline_balance();
```

> **可移植性註記**：PostgreSQL 的 `DEFERRABLE INITIALLY DEFERRED` 約束觸發器能在**交易提交時**才驗證，天然支援「先插單頭、再逐行插入」；SQL Server 無延遲約束，故以 `AFTER` 觸發器 + 應用層保證「單頭與明細在同一交易批次寫入」。實務上 EF Core 會把同一 `SaveChanges` 的 INSERT 包在一個交易內，兩者皆可行。

**期間鎖定觸發器 — SQL Server**：
```sql
CREATE TRIGGER fin.TR_JournalEntry_PeriodCheck
ON fin.JournalEntry
AFTER INSERT
AS
BEGIN

    IF EXISTS (
        SELECT 1
        FROM inserted i

    BEGIN
        RAISERROR('該會計期間非開立狀態或不存在，禁止寫入分錄。', 16, 1);
```

## 5. WAC / 批號成本政策決策表

> 落實檢核 §12.1「WAC/批號政策決策表」、ADR-04（成本政策歸 fin 治理，inv 提供數量與單位成本快照）。

| 情境 | 成本流動假設 | 批號/序號角色 | 庫存成本來源 | 出庫成本（COGS） | 退貨回補成本 |
| --- | --- | --- | --- | --- | --- |
| **預設（採 WAC）** | 加權平均（**以「料件 × 倉庫」為單位**滾算） | **僅追溯與效期管理，不參與成本計算** | `inv.StockBalance.AvgCost`（每倉一個均價） | 出庫當下的 `StockBalance.AvgCost`（鎖入 `StockMovement.UnitCost` 與 `Shipment.UnitCost`） | 以退貨單記載的原 `UnitCost` 回補；**回補後重算該倉 WAC**（修正現況「作廢不還原 WAC」的失真，檢核 §1.4/§4） |
| **選用（批次成本，`Product.CostMethod=1`）** | 各批獨立成本（類 specific-identification） | **參與成本計算**：每批一個成本，出庫須指定批號、扣該批成本 | 批號層成本（需另立 `inv.LotCost(LotId, UnitCost, Qty)`） | 所出批號的批成本 | 退回該批，還原該批 Qty/成本 |

**政策決策（本專案 Phase 2/3）**：
1. **預設一律採 WAC**：`Product.CostMethod=0`。此時**批號/序號只做追溯（哪張單出了哪批、效期到期預警），不做批次成本**——避免兩套成本真相。
2. **WAC 計算粒度＝「料件 × 倉庫」**：因庫存餘額已分倉（`StockBalance`），均價亦分倉滾算。跨倉調撥視為「出庫倉 Out（按來源倉均價）+ 入庫倉 In（按該成本刷入庫倉均價）」。
3. **作廢/退貨還原 WAC**：與現況不同，本設計要求**回補庫存時一併回算 WAC**（用退貨單載的成本），確保均價不失真；此邏輯在 `AccountingService` 強化，DB 端以 `StockMovement` 留軌跡。
4. **若未來導入批次成本**：須 (a) `Product.CostMethod=1`、(b) 新增 `inv.LotCost`、(c) 出庫流程強制指定批號、(d) COGS 改取批成本——**屬獨立政策變更，需另立 ADR**，不在 Phase 2/3 預設範圍。
5. **成本治理歸 `fin`**：`inv` 只提供「數量 + 單位成本快照」；成本流動假設（WAC vs 批次）由 `fin`/會計政策決定（ADR-04），`Product.CostMethod` 視為財務政策欄位。

## 8. 索引、效能與權限收斂

### 8.1 索引策略總則

| 類別 | 規則 |
| --- | --- |
| 多公司前綴 | **凡常用查詢條件，索引第一欄放 `CompanyId`**（配合全域 query filter，見 §9），如 `(CompanyId, Code)`、`(CompanyId, Date)`。 |
| 唯一鍵 | 主檔 `Code`、單據 `Number` 一律 `UX_*_Company_*`（**公司內唯一**，非全域）。 |
| 外鍵欄位 | 所有 FK / 弱參考鍵欄位建索引（避免子表查詢全掃）。 |
| 報表彙總 | `fin.JournalLine(CompanyId, AccountCode)`（科目餘額）、`inv.StockMovement(ProductId, WarehouseId, Date)`（庫存帳）、`fin.Invoice(CompanyId, Period401)`（401 申報）。 |
| 篩選索引 | `app.Outbox`、`AccountingPeriod` 開立判斷等「只查部分列」的場景用 partial/filtered index。 |
| 時間範圍 | 交易表 `Date/EntryDate` 建索引供期間查詢與關帳。 |
| append-only 大表 | `StockMovement`、`JournalLine`、`AuditLog`、`Outbox` 隨時間成長，**規劃日後分割（partition by 月/年）**；本階段先以索引支撐。 |

### 8.2 效能要點

- **報表不跨模組 JOIN**：跨模組彙總（如「銷售毛利」需 sales + inv 成本 + fin 收入）以**讀取模型/物化檢視**（總計畫 `bi` 起步策略）組裝，而非即時跨 schema JOIN，兼顧效能與拆分縫。
- **熱點表並行**：`inv.StockBalance` 是扣帳熱點，靠 `RowVersion` 樂觀鎖 + 短交易；高併發單一料件可考慮應用層序列化或 `UPDLOCK` 提示（SQL Server）/`SELECT ... FOR UPDATE`（PG）。
- **金額一律 `decimal(18,4)`**：杜絕浮點誤差累積（影響借貸平衡 CHECK 成敗）。

### 8.3 權限收斂（落實 append-only / 不可竄改）

- 應用程式連線使用的 DB 帳號：
  - 對 `fin.JournalEntry`/`fin.JournalLine`、`audit.AuditLog`、`inv.StockMovement`、`app.Outbox` 僅授 `SELECT`、`INSERT`，**撤銷 `UPDATE`/`DELETE`**（SQL Server `DENY UPDATE/DELETE`；PG `REVOKE UPDATE, DELETE`）。
  - `Outbox.ProcessedAt` 的更新由**獨立的派送背景帳號**（具該欄 UPDATE 權）處理，與業務帳號分離。
- 結帳/調整等高權限操作走專屬 service + `wf` 簽核，不開放一般帳號直接改期間狀態。

## 9. 多公司資料隔離策略

> 落實 ADR-10、檢核 §12.1。所有業務表帶 `CompanyId`，以**全域查詢過濾**確保使用者只見可及公司資料。

### 9.1 機制

1. **欄位**：每張業務表必有 `CompanyId`（§1.4）。
2. **全域 Query Filter（EF Core）**：在 `OnModelCreating` 對每個含 `CompanyId` 的實體加 `HasQueryFilter(e => e.CompanyId == _currentCompany.Id)`；`_currentCompany` 由請求情境（JWT 內的公司宣告 + `iam.UserCompanyAccess`）提供。應用層**自動**在每個查詢追加 `WHERE CompanyId = @current`，避免漏寫。
3. **列級可見性（多公司使用者）**：使用者可及公司集合來自 `iam.UserCompanyAccess(ScopeType=1)`；切換公司即切換 filter 值。倉/部門級可見性（`ScopeType=2/3`）同理掛在 `inv`/`OrgUnit` 相關查詢。
4. **寫入強制**：新增列時由情境自動填入 `CompanyId`，不信任前端傳入。

### 9.2 索引設計配合

- **`CompanyId` 一律放索引最左欄**：因每個查詢都帶 `WHERE CompanyId=...`，把它放複合索引第一欄可讓所有查詢吃到索引並天然分群，如：
  - `UX_Product_Company_Code (CompanyId, Code)`
  - `IX_JournalEntry_Company_Date (CompanyId, EntryDate)`
  - `IX_JournalLine_Account (CompanyId, AccountCode)`
- 唯一性語意隨之改為「公司內唯一」（料號、單號、科目代碼在不同公司可重複）。

### 9.3 跨公司報表

- 集團合併報表（需跨公司彙總）走**具特權的報表角色**，明確放寬 filter（或以專屬讀取模型彙總），並受 `iam` 權限控管；一般使用者無此權。
