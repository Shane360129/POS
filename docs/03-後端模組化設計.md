## 0. 設計總綱（TL;DR）

本文件把 v2.0 總計畫與檢核報告的決策，落到「**可開工的後端架構**」。最重要的八項決策：

1. **形態先定**：模組化單體，模組間**只走 in-process 介面（`IFinanceService` 等）+ MediatR 領域事件 + Outbox 表**，禁止跨模組直接 JOIN / FK。拆服務設**量化觸發條件**，不到條件不拆。
2. **一致性分兩套**：
   - **預設（單體，現在就做）**：`sales`/`procure` 在**同一 DB 交易**內呼叫 `fin` 產生分錄。**明確修正既有 `AccountingService` 的「雙 `SaveChangesAsync`、無 `BeginTransaction`」bug**（見 §3）。
   - **未來（拆 `fin` 後才啟用）**：Outbox + Saga，且**必含四件套驗收條件**——冪等去重、事件版本/排序、補償失敗人工佇列（dead-letter）、每日強制對帳 + 關期前置檢查（見 §4）。
3. **授權具體化**：RBAC（角色-權限-資源矩陣）+ ABAC（公司/倉/部門/金額上限）；**兩個評估點**（認證中介軟體 + 資源層 policy filter）；**列級**用 EF Core 全域 query filter；**欄位級遮罩**後端 enforce（薪資/成本），前端僅體驗。
4. **會計期間鎖定**：所有寫分錄路徑（含 Cancel / Adjustment）統一經 `IPeriodGuard.EnsureOpen(date)`。
5. **編號服務**：DB sequence / Hi-Lo 取代 `Count()+1`；字軌規則來源集中於 `mdm`。
6. **稽核**：EF `SaveChanges` 攔截器寫 `audit.AuditLog`；分錄 **append-only**、DB 權限收斂（應用帳號無分錄 UPDATE/DELETE）。
7. **API 規範**：REST 路由、ProblemDetails 錯誤模型、統一分頁/排序/篩選、`Idempotency-Key` header、URL 版本；OpenAPI → 產生 TS client（ADR-06）。
8. **安全/可觀測/測試**：收斂 CORS、FluentValidation、速率限制、Secret 管理；Serilog + OpenTelemetry（correlation id 貫穿事件）、健康檢查；WAC 單元、借貸平衡 property-based、關期回歸、（拆分後）契約與對帳測試。

## 1. 第一章：形態、模組邊界與專案結構

### 1.1 為什麼是模組化單體（重申，作為後續所有設計的前提）

檢核報告 §2 已論證：以 1–3 人團隊、12 張表的規模，一步到位 19 微服務是過度設計。本後端**全程以模組化單體交付**，拿到微服務 ~90% 的架構紀律（邊界清楚、可演進），而**不付分散式系統的稅**（分散式交易、最終一致性除錯、N 套 CI/CD、跨服務報表拼裝）。

模組化單體的三條鐵律（對應 ADR-02）：

1. **各模組自有 schema**（`iam.` / `mdm.` / `inv.` / `procure.` / `sales.` / `fin.` / `audit.` / `workflow.` / `notify.`）。
2. **禁止跨模組直接 JOIN，禁止 FK 指向他人核心表**。需要他模組資料時：① 同步讀 → 走 in-process 介面；② 非同步通知 → 走領域事件。
3. **模組間唯一的耦合面是「公開介面 + 公開事件契約」**，實作（`Infrastructure`、`Domain`）對外 `internal`。

### 1.2 模組清單與對外介面（共用基準）

| 模組 | schema | 對外 in-process 介面（範例） | 發佈的領域事件（範例） |
| --- | --- | --- | --- |
| Identity & Access | `iam` | `ICurrentUser`、`IUserDirectory`、`IPermissionService` | `UserProvisioned` |
| Master Data | `mdm` | `INumberingService`、`ITaxService`、`ICurrencyService`、`IPartyService`（客戶/供應商主檔） | `PartyCreated`、`TaxRateChanged` |
| 物料與庫存 | `inv` | `IInventoryService`（取庫存、出/入庫、成本快照） | `GoodsReceived`、`GoodsIssued`、`StockAdjusted` |
| Procurement | `procure` | `IProcurementService` | `PurchaseReceived`、`PurchaseCancelled` |
| Sales / CRM | `sales` | `ISalesService` | `SaleConfirmed`、`SaleReturned`、`SaleCancelled` |
| Finance | `fin` | `IFinanceService`（過帳/沖銷/期間）、`IArApService` | `JournalPosted`、`PeriodClosed` |
| Audit | `audit` | （無業務介面，靠 EF 攔截器） | — |
| Workflow | `workflow` | `IApprovalService`（精簡兩階，先硬編碼） | `ApprovalRequested`、`Approved`、`Rejected` |
| Notification | `notify` | `INotificationService` | — |

> **Backlog 模組邊界（只述不畫）**：`mfg`（工單/BOM 用量/MRP，與 `inv` 走 `IInventoryService` 領退料、與 `fin` 走 `IFinanceService` 歸集成本）、`project`（工時/專案成本，掛 GL 維度）、`assets`（折舊分錄走 `IFinanceService`）、`hr`/`payroll`（薪資分錄走 `IFinanceService`，薪資欄位受欄位級遮罩管控）。這些模組**沿用相同的介面 + 事件 + Outbox 規約**，不另立架構。

### 1.3 解決方案 / 專案結構

採「每模組四層（Domain / Application / Infrastructure / Endpoints）+ 共用 BuildingBlocks + 單一 Host」：

```
src/
├─ Host/
│   └─ InvenFlow.Host.csproj         # 唯一可執行檔；組合所有模組、設定中介軟體管線
├─ BuildingBlocks/
│   ├─ BuildingBlocks.Abstractions/  # IUnitOfWork、IDomainEvent、IIntegrationEvent、ICurrentUser、Result/Error
│   ├─ BuildingBlocks.Infrastructure/# Outbox、EF 攔截器(稽核/Outbox)、TransactionBehavior、分頁、ProblemDetails 對映
│   └─ BuildingBlocks.Web/           # 認證中介、ProblemDetails 中介、Idempotency filter、速率限制、Serilog/OTel 接線
└─ Modules/
    ├─ Iam/
    │   ├─ Iam.Domain/               # 實體、值物件、領域規則（無框架相依）
    │   ├─ Iam.Application/          # 用例(Command/Query Handler)、in-process 介面實作、FluentValidation
    │   ├─ Iam.Infrastructure/       # DbContext(schema=iam)、Repository、Keycloak 整合、Migration
    │   └─ Iam.Endpoints/            # Minimal API / Controller、DTO、OpenAPI 標註
    ├─ Mdm/        { Domain, Application, Infrastructure, Endpoints }
    ├─ Inventory/  { ... }   ├─ Procurement/{ ... }   ├─ Sales/{ ... }
    ├─ Finance/    { ... }   ├─ Audit/{ ... }         ├─ Workflow/{ ... }
    └─ Notification/{ ... }
tests/
├─ <Module>.UnitTests/                # WAC、借貸平衡 property-based、期間規則
├─ Architecture.Tests/                # 邊界守則（NetArchTest：禁跨模組 Infrastructure 互引）
└─ Integration.Tests/                 # Testcontainers 起 SQL Server，端到端交易/關期回歸
```

**邊界由編譯器與測試雙重強制**：

- 模組的 `*.Infrastructure` / `*.Domain` 內部型別宣告為 `internal`；模組間只能參照彼此的 `*.Application` 對外介面（放在 `*.Application` 或獨立的 `*.Contracts`）。
- `Architecture.Tests` 用 **NetArchTest** 斷言：① 任一模組的 `Infrastructure` 不被其他模組參照；② `Endpoints` 不直接相依他模組的 `DbContext`；③ 領域事件契約只放在共用契約組件。違反即 CI 紅燈。

### 1.4 何時、依什麼量化指標才拆成獨立服務（拆分決策準則）

模組化單體是**終點之一**，不是過渡品。**唯有同時滿足下列「至少一條」觸發條件，且通過拆分前置檢查，才把該模組抽離為獨立服務**：

| # | 觸發條件（量化） | 量測來源 |
| --- | --- | --- |
| T1 | 單一模組需要**獨立水平擴縮**：該模組 CPU/RAM 用量持續 > 全進程 60%，且其他模組閒置 | OTel metrics |
| T2 | **團隊/部署節奏衝突**：> 2 個團隊需對不同模組以不同節奏發版，單體部署成為協作瓶頸（每週因互相等待而延遲的部署 ≥ 2 次） | 部署紀錄 |
| T3 | **build / 測試時間**：整體 CI > 20 分鐘且主因可歸於單一模組，模組化拆分可顯著縮短回饋 | CI 報表 |
| T4 | **單庫成為效能瓶頸**：DB CPU 持續 > 70% 或鎖等待顯著，且熱點集中於單一 schema，需獨立資料庫資源 | DB DMV / 監控 |
| T5 | **合規/資安邊界**需物理隔離（如 `iam`、`payroll` 需獨立資料治理域） | 合規需求 |

**拆分前置檢查（缺一不可）**：① 該模組已無跨模組同步交易耦合（或耦合面可用事件取代）；② 對該模組的所有存取已 100% 走公開介面/事件（無偷接 JOIN）；③ 已建立 §4 的對帳與關期前置檢查機制。

**首批可拆對象**：`iam`、`notify`（無交易耦合）。**`fin` 是最後才拆**，且拆 `fin` 必須先完成 §4 全部驗收條件。

## 2. 應用層骨架（CQRS-lite、UnitOfWork、MediatR 管線）

### 2.1 用例風格

- 每個用例 = 一個 **Command 或 Query**（CQRS-lite，不強制讀寫分庫）。Handler 放 `*.Application`。
- Handler 回傳 `Result<T>`（成功值 / `Error`），由 Endpoints 對映成 HTTP（200/201 或 ProblemDetails），**不以例外當控制流**。
- 跨切面以 **MediatR pipeline behaviors** 串接，順序固定：

```
Request
  → LoggingBehavior(correlation id)
  → ValidationBehavior(FluentValidation；失敗 → 400 ProblemDetails，含 errors 字典)
  → AuthorizationBehavior(資源層 policy + ABAC 檢查；失敗 → 403)
  → IdempotencyBehavior(寫入類，依 Idempotency-Key 去重)
  → TransactionBehavior(開啟 DB 交易 / UnitOfWork，含 Outbox 寫入，最後一次提交)
      → Handler(純業務)
```

### 2.2 UnitOfWork 與「單一提交」原則

`TransactionBehavior` 是修正既有雙 `SaveChanges` bug 的**結構性保證**：整個用例**只有一次** `SaveChangesAsync`，且包在一個顯式交易內。Handler 內**不得**自行呼叫 `SaveChangesAsync`。

```csharp
public sealed class TransactionBehavior<TReq, TRes> : IPipelineBehavior<TReq, TRes>
    where TReq : ICommand<TRes>      // 只對寫入命令套交易
{
    private readonly AppDbContext _db;          // 模組共享同一 DbContext（單體：同一連線/交易）
    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        // 若已在外層交易中（巢狀用例），直接沿用，不重複開啟
        if (_db.Database.CurrentTransaction is not null) return await next();

        var strategy = _db.Database.CreateExecutionStrategy();   // 支援連線重試
        return await strategy.ExecuteAsync(async () =>
        {
            await using var tx = await _db.Database.BeginTransactionAsync(ct);
            var res = await next();                  // Handler 內只 Add/Update 實體，不 Save
            // 在提交前，把本交易累積的領域事件轉成 Outbox 訊息（同交易寫入）
            await _outbox.EnqueuePendingAsync(_db, ct);
            await _db.SaveChangesAsync(ct);          // ★ 全用例唯一一次 Save，含業務資料 + Outbox + AuditLog
            await tx.CommitAsync(ct);                // 任一步驟丟例外 → using/strategy 自動 Rollback
            return res;
        });
    }
}
```

> **關鍵**：單體階段，跨模組同步呼叫（如 `sales` 呼叫 `fin`）共享**同一個 `DbContext` 與同一個交易**（見 §3.3 的 DbContext 策略），因此「銷貨 + 分錄」要嘛一起成功、要嘛一起回滾。

## 3. 一致性設計（一）：預設單體 — 同一 DB 交易產生分錄

> 對應 ADR-03、檢核報告 §3.1/§3.3、§12.2。**這是現在就要落地的設計**，也是修正既有 bug 的核心章節。

### 3.1 既有 bug 重述（程式碼證據）

`server/InvenFlow.Api/Services/AccountingService.cs`：

- `ApplyPurchaseAsync`：行 46 先 `SaveChangesAsync()`（寫庫存 + StockMovement），行 67 **再** `SaveChangesAsync()`（寫分錄）。**全程無 `BeginTransaction` / `TransactionScope`**。
- 同樣模式：`ApplySaleAsync`（行 101 / 123）、`ApplyPaymentAsync`（行 130 / 144）、`ApplyReceiptAsync`（行 151 / 165）、`ApplyAdjustmentAsync`（行 188 / 209）。

**後果**：兩次 Save 之間若崩潰（或第二次 Save 失敗），會出現「**庫存已扣 / 已入、分錄未生**」的帳實不符——一個本來用一個本地交易就能保證原子的操作，被拆成兩個非原子步驟。

**附帶問題（一併在 `fin` 重構時處理）**：① `ReverseJournalAsync`（行 278）只抓**第一筆** `!IsReversal` 分錄，沖銷模型脆弱；② Cancel / Adjustment 用 `DateTime.UtcNow` 寫任意日期分錄、**不檢查會計期間**（行 179/190/194/225/...）；③ 借貸平衡只靠程式碼「剛好寫對」，DB 無約束。

### 3.2 修正後的目標流程（以 O2C 銷貨為例）

`sales` 確認出貨時，在**單一用例、單一交易**內完成。`fin` 以 in-process 介面被同步呼叫，**不發事件、不異步**：

```csharp
// Sales.Application — 確認銷貨單用例（節錄；交易由 TransactionBehavior 包覆）
internal sealed class ConfirmSaleHandler : ICommandHandler<ConfirmSaleCommand, SaleResult>
{
    private readonly ISalesRepository _sales;
    private readonly IInventoryService _inventory;   // inv 模組（同交易）
    private readonly IFinanceService   _finance;     // fin 模組（同交易）
    private readonly IPeriodGuard      _period;      // fin：期間開放檢查
    private readonly INumberingService _numbering;   // mdm：DB sequence

    public async Task<Result<SaleResult>> Handle(ConfirmSaleCommand cmd, CancellationToken ct)
    {
        // 0) 期間鎖定：所有寫分錄路徑的統一關卡
        var guard = await _period.EnsureOpenAsync(cmd.CompanyId, cmd.Date, ct);
        if (guard.IsFailure) return guard.Error;            // → 422 PeriodClosed

        // 1) 取號（sequence，非 Count()+1）
        var number = await _numbering.NextAsync(cmd.CompanyId, "SO", cmd.Date, ct);

        // 2) 出庫 + 鎖 COGS（inv 回傳每行單位成本快照；庫存不足 → 領域錯誤 → 409）
        var issue = await _inventory.IssueAsync(new IssueRequest(cmd.WarehouseId, cmd.Lines), ct);
        if (issue.IsFailure) return issue.Error;

        // 3) 建立銷貨單（含稅額；稅率來自 mdm）
        var sale = Sale.Create(cmd, issue.Value.UnitCosts, number);
        _sales.Add(sale);

        // 4) ★同交易★呼叫 fin 產生分錄（借應收/貸收入/貸銷項稅、借成本/貸存貨）
        var post = await _finance.PostSaleJournalAsync(sale.ToJournalRequest(), ct);
        if (post.IsFailure) return post.Error;

        // 不在此 Save；TransactionBehavior 統一提交。任一步失敗 → 整筆回滾，不會帳實不符。
        return new SaleResult(sale.Id, number);
    }
}
```

`IFinanceService.PostSaleJournalAsync` 在 `fin` 模組內建立 `JournalEntry` + `JournalLine`（沿用 `AccountingService` 的科目邏輯：現金/應收、銷貨收入、銷貨成本、存貨，新增**銷項稅**），但：

- **不自行 Save**（交給外層 UnitOfWork）。
- **過帳前呼叫 `IPeriodGuard`**（雙重保險）。
- **建立時即驗借貸平衡**：`Σ(Debit) == Σ(Credit)`，違反丟領域例外；DB 端另有 CHECK / 觸發器（見 `02-資料庫設計.md`）作為第二道防線。

### 3.3 單體階段的 DbContext / 交易邊界策略

為了讓「跨模組同步呼叫共享同一交易」成立，採以下其一（建議 A）：

- **方案 A（建議）— 每模組一個 `DbContext`、共享同一 `DbConnection` + `DbTransaction`**：各模組 `DbContext` 只映射自己的 schema（維持 schema 隔離與遷移獨立），但在請求範圍內共用同一條連線；`TransactionBehavior` 在最外層開交易，內層 `DbContext` `UseTransaction(sharedTx)`。提交時逐一 `SaveChanges` 後 `Commit`。**兼顧模組邊界與本地 ACID。**
- **方案 B（更簡單，過渡可用）— 單一 `AppDbContext`、以 schema 區隔實體**：所有實體在同一 context，天然同交易。代價是模組共用 context、邊界較弱；可作為 Phase 1.5 起步，之後演進到 A。

> 不論 A/B，**對外契約（介面 + 事件）不變**，故日後拆 `fin` 時 `sales` 的呼叫端改動極小（把 `IFinanceService` 換成遠端代理 + 改走事件，見 §4）。

### 3.4 失敗回滾範例與保證

| 失敗點 | 既有行為（bug） | 修正後行為 |
| --- | --- | --- |
| 出庫成功、寫分錄前崩潰 | 庫存已扣、分錄未生（帳實不符） | 交易未提交 → **庫存扣帳一併回滾**，無殘留 |
| 分錄借貸不平 | 可能寫入（無約束） | 建立時即丟例外 → 整筆回滾；DB CHECK 為第二道 |
| 寫入已關期間 | 直接寫入 | `IPeriodGuard` 422 → 整筆回滾 |
| 單號併發碰撞 | `Count()+1` 重號 | sequence 保證唯一，且唯一索引為最後防線 |

### 3.5 作廢 / 沖銷 / 退貨的一致性（補強既有脆弱點）

- **作廢（Cancel）**：在同一交易內，① `inv` 反向庫存異動、② `fin` 產生**沖銷分錄**、③ 期間檢查。沖銷分錄改為**以 `RefType+RefId` 抓出原分錄的全部非沖銷 lines 逐筆反向**（修正 `ReverseJournalAsync` 只抓第一筆的問題），並標記 `IsReversal=true`、回填 `ReversesJournalEntryId`。
- **跨期作廢**：原單在已關期間時，**沖銷分錄記在當期**（Spike B 驗證），不回寫已關期間。
- **退貨 / 折讓（新增）**：部分退貨在同一交易內回補庫存（WAC 政策：以退貨當下成本或原單成本，依 `02` 決策）、開紅字發票、沖減 AR/AP；同樣經期間檢查與借貸平衡。
- **作廢還原 WAC**：既有刻意不還原（行 221）會使均價失真。成本政策歸 `fin` 治理（ADR-04），`inv` 僅提供數量與單位成本快照；還原策略由 `02` 與 Spike 決定，本文僅要求「**走同一交易、可被對帳驗證**」。

## 4. 一致性設計（二）：未來拆分後 — Outbox + Saga（四件套驗收條件）

> **僅當 §1.4 觸發條件成立、決定把 `fin`（或其他交易模組）抽離為獨立服務時才啟用。** 在此之前 Outbox 表先建好（欄位含 `EventId`），但**分錄維持同步同交易**。下列四項列為**拆分驗收條件（Acceptance Criteria），缺一不可上線**。

拆分後流程改為：`inv`/`sales` 在本地交易內寫業務資料 **+ Outbox**（同交易）→ 背景 dispatcher 投遞至訊息匯流排（起步 RabbitMQ，非 Kafka）→ `fin` 消費並產生分錄。一個 ACID 本地交易被換成跨服務最終一致，故必須補齊：

### AC-1 冪等（`EventId` 去重表）

- 每則整合事件帶唯一 `EventId`（GUID）。
- `fin` 端建 `fin.ProcessedEvent(EventId PK, ProcessedAt)`；消費時**先在同一交易內 INSERT `ProcessedEvent`**，主鍵衝突即視為重複、跳過。
- **驗收**：對同一 `EventId` 重投 N 次，分錄只產生一次（避免「試算表仍平衡但金額翻倍」）。

### AC-2 事件版本 / 排序

- 整合事件帶 `AggregateId` + `AggregateVersion`（單調遞增）+ `OccurredAt`。
- `fin` 端記錄各 `AggregateId` 已處理的最大 version；收到**較舊或重複 version 丟棄**，收到**跳號**則暫存等待（或進 dead-letter 待人工）。
- **驗收**：故意亂序投遞「出貨」「作廢」，`fin` 不會對不存在分錄沖銷、不會先沖再記。

### AC-3 補償失敗的人工佇列（dead-letter）

- 消費/補償重試達上限仍失敗 → 進 `fin.DeadLetter`（含原事件、錯誤、重試次數），並告警（`notify`）。
- 提供**人工重放 / 標記已處理**的管理端點，禁止靜默丟棄。
- **驗收**：注入補償失敗，事件落入 dead-letter 且可被人工重放成功。

### AC-4 每日強制對帳 + 關期前置檢查

- **每日對帳作業（背景排程）**，至少三組：
  1. **庫存彙總 ↔ GL 存貨科目**：`Σ(inv 各倉成本)` vs `fin` 存貨科目餘額。
  2. **AR 明細 ↔ 應收科目**：`sales` 未沖銷 AR 明細合計 vs `fin` 應收科目餘額。
  3. **AP 明細 ↔ 應付科目**：`procure` 未沖銷 AP 明細合計 vs `fin` 應付科目餘額。
  - 差異 → 自動開**對帳差異工單**（dead-letter / 工作佇列），不可自動忽略。
- **關期前置檢查（`PeriodCloseGuard`，關期作業必經）**，三條件全綠才允許 `PeriodClosed`：
  1. **Outbox 無未發**（所有 producer 的 pending = 0）。
  2. **消費端無 backlog**（`fin` 消費延遲 = 0、無未處理跳號）。
  3. **對帳無差異**（當期三組對帳皆 0 差異）。
- **驗收**：在途事件未落帳 / 對帳有差異時，關期被擋下並回報原因（達成「靜止點 quiescence」才可關期）。

> 對應檢核報告 §3.2 列出的所有風險（重複、亂序、補償失敗、COGS 時點漂移、跨服務沖銷、結帳前置、對帳）皆由 AC-1~AC-4 覆蓋。**Spike A 即為驗證這四件套能否抓出注入的故障**（見 §11）。

## 5. 授權模型（RBAC + ABAC，兩個評估點，列級 + 欄位級）

> 對應 ADR-05、檢核報告 §5、§12.2。原則：**認證集中（Keycloak）、授權分散（各模組）；前端遮罩只是體驗，真正權限在後端 enforce。**

### 5.1 認證（Keycloak / OIDC）

- Keycloak 發 JWT；Host 的**認證中介軟體驗 JWT**（簽章、`iss`、`aud`、過期）。`Program.cs` 目前**無** `AddAuthentication/Authorization`，第一步即補上 `AddAuthentication().AddJwtBearer(...)` + `AddAuthorization()`，並對所有 endpoint 預設 `[Authorize]`（白名單例外：health、swagger）。
- JWT 內帶 `sub`、`roles`、以及 ABAC 屬性宣告（`company_ids`、`warehouse_ids`、`dept_id`、`approval_limit`）。屬性主檔在 `iam`，登入時由 Keycloak mapper 或 `iam` token 加工注入；`ICurrentUser` 統一讀取。

### 5.2 RBAC：角色-權限-資源矩陣

- **權限（Permission）** 命名：`<module>.<resource>.<action>`，例：`sales.order.create`、`fin.journal.post`、`fin.period.close`、`procure.po.approve`。
- **角色（Role）** 綁定權限集合；使用者綁角色（可多角色，權限取聯集）。`iam` 維護，`IPermissionService` 提供查詢。

**範例角色-權限-資源矩陣**（節錄）：

| 角色 \ 權限 | sales.order.* | sales.return.create | inv.stock.adjust | procure.po.approve | fin.journal.post | fin.period.close | hr.payroll.read |
| --- | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 業務員 Sales | C/R/U | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 銷售主管 SalesMgr | C/R/U/作廢 | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 倉管 WarehouseOp | R | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ |
| 採購主管 ProcureMgr | ✗ | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ |
| 會計 Accountant | R | R | R | ✗ | ✓ | ✗ | ✗ |
| 財務長 CFO | R | R | R | ✓ | ✓ | ✓ | ✓(遮罩解除) |
| 系統管理員 Admin | 設定類權限；**預設無 `fin.journal.*`（職責分離）** | | | | | | |

> 職責分離（SoD）：`Admin` 不應自動取得過帳權；過帳/關期屬會計/財務角色。

### 5.3 ABAC：屬性與資源層 policy

RBAC 決定「能不能做這類動作」，ABAC 決定「能不能對**這一筆/這個範圍**做」。屬性：

| 屬性 | 來源 | 用途 |
| --- | --- | --- |
| `company_ids` | iam（多公司租戶） | 只能存取可見公司的資料 |
| `warehouse_ids` | iam | 倉管只能調整自己負責倉 |
| `dept_id` | iam | 部門別資料 / 維度 |
| `approval_limit` | iam | 簽核 / 單據金額上限（如採購主管限 50 萬） |

資源層以 **policy + `IAuthorizationHandler`**（或 §2.1 的 `AuthorizationBehavior`）評估，例：核准採購單時檢查 `po.Amount <= currentUser.ApprovalLimit && po.CompanyId ∈ company_ids`，否則 403。

### 5.4 兩個授權評估點

1. **評估點一：認證中介軟體**（粗粒度）——驗 JWT、載入身分與權限/屬性到 `ICurrentUser`；端點層 `RequirePermission("fin.journal.post")` 擋掉無權限者。
2. **評估點二：資源層 policy filter**（細粒度）——在用例內以 ABAC 對**具體資源**判斷（公司/倉/部門/金額）。**寫入路徑一律雙重把關**，不可只靠端點層。

### 5.5 列級過濾（EF Core 全域 query filter）

依使用者可見公司/倉，於各 `DbContext` 註冊全域 query filter，**所有查詢自動套用**（讀寫一致），避免「忘了加 WHERE」造成越權讀取：

```csharp
// 於模組 DbContext OnModelCreating，對帶 CompanyId 的實體統一套用
modelBuilder.Entity<Sale>().HasQueryFilter(s =>
    _tenant.CompanyIds.Contains(s.CompanyId)
    && (_tenant.WarehouseIds.Count == 0 || _tenant.WarehouseIds.Contains(s.WarehouseId)));
```

- `_tenant`（`ICurrentTenantContext`，scoped）由認證中介注入；背景作業 / 系統流程以特權 scope 執行（明確標註，避免漏資料）。
- **跨公司報表**等合法越界，走**明確的特權查詢路徑**（`IgnoreQueryFilters()` + 需 `report.cross-company.read` 權限），不得隨意關閉 filter。

### 5.6 欄位級遮罩（後端 enforce）

- 敏感欄位（薪資 `payroll.*`、成本 `inv.AvgCost` / `SaleItem.UnitCost`、客戶聯絡資料）在**回應序列化或映射 DTO 時**，依權限判斷是否遮罩/移除。
- 機制：用例回傳 DTO 時，經 `ISensitiveFieldPolicy` 決定欄位可見性（無 `inv.cost.read` → `unitCost = null`）。**後端是唯一真相**；前端僅依回傳是否為 null 決定顯示，不得依賴前端隱藏。
- **驗收**：以低權限 token 直呼 API，敏感欄位必為遮罩值（測試覆蓋，見 §10）。

## 6. 會計期間鎖定（統一關卡）

> 對應 ADR-07、檢核報告 §5（🔴）。修正既有 Cancel/Adjustment 可寫任意日期分錄、不檢查期間的問題。

- `fin` 維護 `AccountingPeriod`（每公司每期，狀態 `Open / Closed / Locked`，見 `02`）。
- **所有寫分錄路徑（建立、作廢、調整、退貨、折讓、結轉）一律先呼叫 `IPeriodGuard.EnsureOpenAsync(companyId, date)`**；非 Open → 回 `PeriodClosed`（HTTP 422）。
- 防繞過：① 應用層由 `fin` 的過帳服務統一入口（其他模組不得自行 `Add(JournalEntry)`）；② DB 端對 `JournalEntry` 寫入以觸發器檢查對應期間狀態（第二道，見 `02`）。
- **跨期沖銷**：原單在已關期間 → 沖銷/更正分錄記入**當期**（Spike B 驗證）。
- **關期動作**本身：開放期 → Closed 需 `fin.period.close` 權限；拆分後另須通過 §4 的 `PeriodCloseGuard` 三條件。

## 7. 編號服務（DB sequence / Hi-Lo）

> 對應 ADR-09、檢核報告 §4。修正 `NextNumberAsync` 用 `Count()+1`（行 300-315）併發/作廢後重號的 bug。

- 介面 `INumberingService.NextAsync(companyId, docType, date)` 由 `mdm` 實作。
- **取號機制**：用 **DB sequence**（SQL Server `CREATE SEQUENCE` / EF Core `HasSequence`）或 **Hi-Lo**（批次取段，減少往返），**不依賴資料列計數**，故作廢/併發都不重號。
- **字軌規則來源集中於 `mdm`**：`NumberRule(CompanyId, DocType, Prefix, 日期格式, 流水位數, 是否每日/每月歸零)`。例：`SO + yyyyMM + 4 位流水`，每月歸零。
- 唯一索引（既有 `Purchase.Number` 等已有 unique index）作為**最後防線**：萬一邏輯出錯造成重號，DB 直接擋下，不會落地髒資料。
- 與交易的關係：取號在用例內、交易中進行；sequence 的值即使交易回滾也會「跳號」（可接受，單號連續性非帳務正確性需求）。

## 8. 稽核（EF SaveChanges 攔截器 + 不可竄改）

> 對應 ADR-08、檢核報告 §5、§12.2。`audit` 做成**同源攔截器**而非異步消費服務，避免稽核事件遺失。

### 8.1 稽核軌跡

- 在 `SaveChangesInterceptor` 內，於 `SavingChanges` 掃描 `ChangeTracker` 的 Added/Modified/Deleted 實體，寫入 `audit.AuditLog`（who=`ICurrentUser.Id`、when、entity、PK、操作、變更前後值 JSON、correlation id）。
- **與業務同交易**：攔截器產生的 `AuditLog` 隨同一次 `SaveChanges` 落地（§2.2 的單一提交），保證「有業務變更就有稽核」。
- 共用欄位 `CreatedBy/At`、`UpdatedBy/At` 由攔截器自動填入（不靠各 Handler 手寫）。

### 8.2 分錄不可竄改（append-only）

- **應用層**：`fin` 不提供分錄 UPDATE/DELETE 用例；更正一律以**沖銷分錄**處理（§3.5）。
- **DB 權限收斂**：應用程式連線帳號對 `fin.JournalEntry` / `fin.JournalLine` 只授 `INSERT/SELECT`，**撤銷 UPDATE/DELETE**（見 `02`）。即使應用層被繞過，DB 也擋下竄改。
- 沖銷可追溯：`JournalEntry.ReversesJournalEntryId` 回指原分錄，形成可稽核鏈。

## 9. API 設計規範

> 對應 ADR-06。OpenAPI 為唯一契約來源，前端不手寫型別。

### 9.1 路由風格

- REST 資源式：`/api/v1/{module}/{resource}`，例：`/api/v1/sales/orders`、`/api/v1/fin/journals`。
- 集合用複數；子資源巢狀僅一層；**動作型操作**（過帳/作廢/退貨）用子路徑 POST：`POST /api/v1/sales/orders/{id}/confirm`、`/cancel`、`/returns`。
- 版本：**URL 路徑版本 `/v1`**（簡單、好快取、對 OpenAPI 友善）；破壞性變更升 `/v2`，舊版維持至消費端遷移完成。

### 9.2 錯誤模型（ProblemDetails，RFC 7807）

統一以 `application/problem+json` 回傳；以 `ProblemDetailsMiddleware` 把 `Result.Error` / 例外對映：

| 情境 | HTTP | `type`（範例） |
| --- | --- | --- |
| 驗證失敗（FluentValidation） | 400 | `.../validation`（含 `errors` 欄位字典） |
| 未認證 | 401 | `.../unauthorized` |
| 無權限（RBAC/ABAC） | 403 | `.../forbidden` |
| 找不到 | 404 | `.../not-found` |
| 庫存不足 / 狀態衝突 | 409 | `.../conflict` |
| 業務規則（期間已關、借貸不平） | 422 | `.../period-closed`、`.../unbalanced-journal` |
| 冪等鍵衝突（同鍵不同內容） | 422 | `.../idempotency-conflict` |

每個回應含 `traceId`（= correlation id），便於追蹤。

### 9.3 分頁 / 排序 / 篩選（統一）

- 查詢參數：`?page=1&pageSize=20&sort=-date,number&filter[status]=Active&filter[date_gte]=2026-01-01`。
- 回應信封：`{ items: [...], page, pageSize, total }`（取代既有 controller 直接回 list / 匿名物件、無分頁、`Take(500)` 硬上限的作法）。
- 大型清單（StockMovement、Journal）一律分頁；預設 `pageSize` 上限（如 100）。

### 9.4 冪等鍵 header

- 寫入類（POST 建單 / 過帳 / 作廢）支援 `Idempotency-Key` header。
- `IdempotencyBehavior`（§2.1）以 `(key, 端點, 請求雜湊)` 在 `mdm.IdempotencyRecord` 去重：同鍵同內容回首次結果；同鍵不同內容 → 422。
- **拆分後**此 header 與 §4 的 `EventId` 去重一起構成端到端 exactly-once 語意。

### 9.5 OpenAPI → TS client（ADR-06）

- 啟用 Swashbuckle 產生 OpenAPI v3；CI 以 `openapi-typescript` / `openapi-generator` 產 TS client 與型別，供前端 `04` 使用。
- 契約測試：CI 比對 OpenAPI 變更，破壞性變更需升版並告警。

### 9.6 核心模組代表性 endpoint 清單（聚焦關鍵單據 + 過帳/作廢/退貨）

## 11. 可觀測性

> 對應檢核報告 §8（單體階段從簡）。

- **結構化日誌**：Serilog，輸出至 Seq / Grafana Cloud；每筆日誌帶 `traceId`（correlation id）。
- **OpenTelemetry**：Tracing + Metrics。**correlation id 貫穿事件**——HTTP 進來產生 / 沿用 `traceId`，寫入 Outbox 訊息的 metadata，dispatcher/consumer 還原為同一 trace（為日後拆分預留端到端追蹤）。
- **健康檢查**：`/health/live`（進程存活）、`/health/ready`（DB、Keycloak、（拆分後）訊息匯流排可用）；供容器/PaaS 探針。
- **關鍵 metrics**：用例延遲、Outbox pending 數、（拆分後）消費延遲與 dead-letter 數、對帳差異筆數（直接餵 §1.4 觸發條件與 §4 關期檢查）。

## 13. Spike 章節（設計前置實驗與驗收標準）

> 對應檢核報告 §6.3。**正式大規模實作前先做，風險可控才繼續。**

| Spike | 目標 | 做法 | 驗收標準（通過才繼續） |
| --- | --- | --- | --- |
| **A — 跨模組財務一致性** | 決定未來是否值得拆 `fin` | 用 `inv`+`fin` 兩端 + Outbox + RabbitMQ，做「出貨→COGS 入帳」端到端，**注入重複/亂序/補償失敗** | §4 的 AC-1~AC-4 能 100% 抓出注入故障（去重、丟棄舊版、進 dead-letter、對帳報差異、關期被擋）。**做不漂亮 → 結論為「不拆 `fin`，維持 §3 同交易」** |
| **B — 期間鎖定 + 跨期沖銷** | 驗證 §6 機制 | 實作 `AccountingPeriod` + `IPeriodGuard`；測「關期後不能寫該期分錄」「跨期作廢走當期沖銷」 | 已關期間寫入被擋（422）；跨期作廢分錄正確記入當期；試算表前後平衡 |
| **C — 多公司/多幣別橫切成本** | 校準工時 | 在既有 12 表加 `CompanyId` + 原幣/本位幣，量測對查詢/query filter/分錄的改動幅度 | 產出改動清單與工時估計；確認全域 query filter 方案可承載多公司列級過濾 |
| **D — 台灣統一發票/折讓模型化** | 驗證對 Sale/Journal 侵入度 | 把字軌、進/銷項稅、紅字折讓模型化，跑通一張含稅銷貨 + 一張折讓 | 含稅分錄借貸平衡、稅額科目正確；折讓正確沖減 AR 與紅字；侵入度可接受 |
