## 0. 總評（Executive Summary）

**結論：方向正確，但「成熟度」被高估，且計畫對自身現況的描述有數處與程式碼不符，會直接污染後續三份設計文件的前提假設。**

這份計畫的「敘事品質」很高：有願景、有 ADR、有 Roadmap、有風險表，骨架完整、用詞專業。但作為一份要拿來指導實作的工程藍圖，它有三個結構性問題：

1. **現況描述不準確**——其中最關鍵的一條（「WAC 與分錄在單一 DB 交易內完成」）**與程式碼不符**：實際上 `AccountingService` 連單體版都沒有用交易包起來（一個操作內 `SaveChangesAsync` 被呼叫兩次，中間無 `BeginTransaction`）。一份要「拆解既有一致性保證」的計畫，卻把「目前根本不存在的一致性保證」當成既有資產，這會誤導 Phase 3 的設計。
2. **規模與架構嚴重不匹配（over-engineering）**——把一套單人/小團隊的 12 張表 demo，一步到位規劃成 **19 個微服務 + Kafka 升級路線 + K8s + gRPC + Saga 編排 + 資料倉儲**。以這個團隊規模與業務量，這是教科書級的過度設計，維運成本會壓垮交付。
3. **對「ERP 真正難的地方」著墨太少**——稅務/發票（台灣統一發票與營業稅）、退貨/折讓、序號批號效期、會計期間結轉與鎖定的**具體機制**、列級權限——這些才是 ERP 的深水區，計畫多半只用一個名詞帶過，沒有設計含金量。

**成熟度評分：B−（願景 A，工程藍圖 C＋）。**
作為「願景與範圍對齊文件」可用；作為「能直接開工的架構決策」尚不可用，需依本報告的 Must-fix 清單修訂後，才適合往下展開 02/03/04 設計。

**最重要的一句話建議**：**先把目標從「微服務 ERP」改成「模組化單體（Modular Monolith）ERP，預留拆分縫」**，把 Kafka/K8s/gRPC/Saga 全部降級為「Phase 5 之後、有明確量化觸發條件才啟用」的選項。其餘九成的業務價值都能在單體內先做出來。

## 2. 微服務取捨：是否該拆？切得對不對？

### 2.1 核心判斷：以此規模，19 個微服務是過度設計 🔴

幾個量化事實：
- 現況是 **12 張表、5 類報表、單一資料庫、單一 `.csproj`**。
- 計畫假設「團隊具 C# 能力」「初期單一資料中心」，但**沒有任何一處說明團隊人數**。從 repo 規模與單人 commit 風格判斷，這比較像 1–3 人團隊。
- 微服務的損益平衡點通常出現在「多個團隊需要獨立部署節奏」「單體已大到 build/部署/領域邊界成為瓶頸」。**這套系統離那個點還很遠。**

微服務在此引入的固定成本（每一項都要乘以 19）：分散式交易、最終一致性除錯、跨服務 schema 演進、契約版本管理、分散式追蹤、N 套 CI/CD 與部署、服務發現、跨服務查詢/報表的拼裝、本機開發要起一堆容器。**這些成本是確定的；而獨立擴縮、團隊自治這些收益，在 1–3 人團隊身上幾乎為零。**

> Martin Fowler 的「MonolithFirst」與 Sam Newman 的拆分前提（先有清楚模組邊界、有運維成熟度）都站在計畫的反面。計畫的 ADR-01 自己也寫了 Strangler Fig「先模組化單體再拆」——**但 Roadmap（Phase 2/3）卻是直接拆成服務**，ADR 與 Roadmap 自相矛盾（見 §6.2）。

### 2.2 建議的目標形態：Modular Monolith（模組化單體）+ 拆分縫

把「19 個微服務」改成「**1 個部署單元、19 個（或更少）模組**」，模組間：
- 各自獨立的 schema / 命名前綴，**禁止跨模組直接 JOIN 他人資料表**（用 EF 的 schema 隔離 + 程式碼層 internal 邊界強制）。
- 模組間呼叫走**記憶體內的介面**（`IInventoryModule`），而非 HTTP/gRPC——保留日後把介面換成遠端代理的縫。
- 領域事件用**同行程的 in-process bus**（如 MediatR notifications）+ **Outbox 表**，介面與微服務版一致；日後要拆，只需把 in-process bus 換成 RabbitMQ，事件契約不動。

這樣可以**拿到微服務 90% 的架構紀律（邊界清楚、可演進），而不付分散式系統的稅**。真要拆，先拆「最該獨立」的 1–2 個（通常是 `iam` 與 `notify`／`docs-svc`，因為它們無交易耦合）。

### 2.3 邊界切得太細／太粗的具體意見

| 計畫服務 | 評斷 | 建議 |
| --- | --- | --- |
| `iam`（1） | 合理，且是唯一**真有理由先獨立**的（安全邊界、可換 Keycloak/Duende） | 保留為可獨立服務（或直接用現成 IdP，見 §8） |
| `gateway`（2） | 模式對，但對單體而言**現在就上 YARP 是過早**；單體階段用 ASP.NET 中介軟體即可 | 降級到 Phase 4+ |
| `workflow`（3）、`notify`（4）、`audit`（5）、`docs-svc`（6）、`bi`（7） | 平台服務切得**合理**；但 `audit` 不該是「事件消費的獨立服務」起步——稽核必須**與業務交易同源可靠**，做成獨立服務反而引入「稽核事件遺失」風險 | `audit` 起步做成**單體內的攔截器/EF SaveChanges 攔截 + 同庫稽核表**；`bi` 起步用**讀取複本/物化檢視**，別一開始就資料倉儲 |
| `product`（8）/ `inventory`（9） | **切得有風險**。WAC 成本、庫存、料件主檔三者在「進貨入庫刷新均價」時是**強耦合**；硬拆會把一個本地交易變成跨服務 Saga（見 §3） | **合併** `product`+`inventory` 為一個「物料與庫存」模組/服務 |
| `procure`（10）/ `sales`（11） | 邊界合理 | 保留為模組 |
| `crm`（12） | 與 `sales` 的 Customer 高度重疊；獨立 CRM 對中小企業常是空殼 | **併入 `sales`** 或延後；客戶主檔放 `mdm` |
| `finance`（13） | 合理（GL 本就該獨立帳務邊界），但「分錄改由消費事件產生」風險極高（見 §3） | 邊界保留，**一致性機制要重做** |
| `mfg`/`project`/`assets`/`hr`/`payroll`（14–18） | 都是「新增」，**目前 0 程式碼**。把 5 個尚不存在的領域先畫成 5 個服務，是**規劃先於需求** | 全部標為「**未來模組、需求未驗證**」，不納入前 4 個 Phase 的架構承諾 |
| `mdm`（19） | 觀念對（共用代碼/幣別/稅率/編號規則），且**應該先做**，因為 §現況的 `NextNumberAsync` 用 `Count+1` 產號有併發重號 bug（見 §4） | **提前**到地基階段，作為單體內共用模組 |

**邊界結論**：把 19 收斂到「**第一階段真正要做的 6–8 個模組**」：`iam`、`mdm`、`物料庫存(product+inventory)`、`procure`、`sales(含 crm 基本)`、`finance`、`audit(攔截器)`、`workflow`。其餘 11 個降為 backlog。

## 3. 跨服務資料一致性：把分錄改為「finance 消費事件」的風險 🔴

這是整份計畫**技術風險最高、最值得對抗式檢視**的決策（ADR-03 + ADR-04）。

### 3.1 現況其實是「一個本地交易」就能保證的事，被換成最難的分散式問題

現在（程式碼）：銷售 = 扣庫存 + 鎖 COGS（用當下 WAC）+ 寫 4 條分錄（借應收/貸收入、借成本/貸存貨），全在同一個 `AppDbContext`（雖然目前少了顯式交易，補上即原子）。**這是 RDBMS 最擅長的事。**

計畫之後：`inventory` 出貨 → 發「出貨完成（含 COGS 金額）」事件 → `finance` 消費 → 產生分錄。**一個 ACID 本地交易被換成跨服務最終一致**。除非有極強的擴展性理由，否則這是用大砲打蚊子。

### 3.2 Outbox + Saga「不夠」——以下都是計畫沒談、但會出事的點

| 風險 | 說明 | 計畫是否涵蓋 |
| --- | --- | --- |
| **重複事件（at-least-once）** | Outbox/訊息匯流排幾乎都是「至少一次」投遞，`finance` 會收到重複的「出貨完成」。若沒有**冪等鍵**（如 `eventId` 去重表），會產生**重複分錄 → 試算表仍平衡但金額翻倍**，極難察覺 | ❌ 未提冪等 |
| **亂序（out-of-order）** | 「銷售出貨」與「銷售作廢」事件若亂序到達，`finance` 可能先沖銷再入帳，或對不存在的分錄沖銷 | ❌ 未提排序/版本 |
| **補償失敗** | Saga 補償交易本身也會失敗（`finance` 入帳成功但 `inventory` 後續步驟失敗，回頭要沖帳卻沖不掉）。需要**人工介入佇列 + dead-letter** | ❌ 只寫「補償交易」一詞 |
| **COGS 與庫存的時點漂移** | WAC 留在 `inventory`，但分錄在 `finance` 異步生成。在事件**在途**期間，`inventory` 的存貨數量已減、`finance` 的「存貨」科目餘額**尚未減**——任一時刻做**試算表 vs 存貨明細對帳，帳實必然短暫不符**。月結/期末若卡在這個窗口，會計無法結帳 | ❌ 完全未談這個語意鴻溝 |
| **作廢沖銷的跨服務正確性** | 現況作廢「不還原 WAC」（行 221）。拆服務後，作廢要跨 `inventory`+`finance` 沖銷，且 WAC 漂移問題被放大；若中途失敗，存貨數量、均價、GL 三者各自停在不同狀態 | ❌ |
| **期間結轉（period close）** | 結轉是「把某期間所有分錄凍結、結出損益、轉入保留盈餘」。事件驅動下，**如何保證「結帳當下，所有在途事件都已落帳」**？需要**靜止點（quiescence）/ 對帳關卡**才能安全關期 | ❌ 未提結帳前置條件 |
| **對帳（reconciliation）** | 分散式財務系統的命脈是**定期自動對帳**：庫存明細彙總 vs GL「存貨」科目、AR 明細 vs「應收」科目、事件已發 vs 已消費。計畫只在風險表寫「對帳批次」四個字，無設計 | ❌ 嚴重不足 |

### 3.3 建議（按優先序）

1. **🔴 不要在 Phase 2/3 把分錄事件化。** 在模組化單體內，讓 `finance` 模組**同步、同交易**地被 `sales`/`procure` 呼叫產生分錄（沿用現有 `AccountingService` 思路，但補上顯式交易與借貸平衡 CHECK）。這保留現有的 ACID 正確性。
2. 若**未來**真要拆 `finance`：採「**事件 + 冪等 + 對帳**」三件套：
   - 每個整合事件帶 `eventId` + `aggregateVersion`；`finance` 端建**已處理事件表**做去重與順序檢核。
   - **每日強制對帳作業**：庫存彙總 vs GL 存貨科目、AR/AP 明細 vs 對應科目，差異進工單。
   - **關期前置檢查**：確認 outbox 無未發、消費端無 backlog、對帳無差異，才允許 period close。
3. **把「COGS 算在哪」想清楚**：ADR-04 讓 `inventory` 算 COGS 再丟給 `finance`，等於把「會計政策（成本流動假設）」分散到兩個服務。建議**成本政策歸 finance/會計治理**，`inventory` 只提供數量與單位成本快照，避免兩邊各有一套「成本真相」。

## 4. 缺漏的模組與關注點（對「全功能 ERP」）

計畫列了 19 個服務，但**ERP 真正的深水區**多半只有名詞、沒有設計。以下是對「全功能」而言的實質缺口：

| 缺漏 | 嚴重度 | 說明與證據 |
| --- | --- | --- |
| **稅務 / 統一發票 / 營業稅** | 🔴 | 現況 `Purchase`/`Sale`/`Item` **完全無稅額欄位**；分錄也無「進項/銷項稅額」科目（`SeedData` 科目表只有 8 個，無 2130 銷項稅、1140 進項稅）。台灣 ERP 沒有統一發票（B2B/B2C、字軌、作廢/折讓、媒體申報 401/403）幾乎不能營運。計畫只在 cross-cutting 提一句「稅率」。**這應是一個一級主題。** |
| **退貨 / 銷貨折讓 / 進貨退出** | 🔴 | 現況只有「整單作廢」，**沒有部分退貨、折讓**。退貨牽動庫存回補（且 WAC 如何處理）、紅字發票、AR/AP 沖減——是日常高頻交易，計畫只字未提。 |
| **序號 / 批號 / 效期 / 保固** | 🟠 | `inventory` 服務描述有提「批號/序號」，但**無任何資料模型設計**，且與 WAC（批次成本 vs 平均成本）有政策衝突，需要決策。效期（食品/醫材）完全未談。 |
| **報價 / 合約 / 價目表 / 折扣政策** | 🟠 | `sales`/`crm` 提到報價、合約名詞，但定價引擎（多階價目、客戶專屬價、量價、促銷）無設計。現況 `SaleItem.UnitPrice` 直接抄商品定價。 |
| **預算 / 成本中心 / 部門別損益** | 🟠 | GL 只有科目，**無維度（dimension）**：部門、成本中心、專案、據點。沒有維度就出不了「部門損益」「專案成本」——而計畫又把 `project`/`mfg` 成本歸集列為目標，前後矛盾。 |
| **列級 / 欄位級資料權限** | 🟠 | 計畫 cross-cutting 寫「欄位級遮罩」「最小權限」，但**無機制設計**：誰能看哪個倉/哪間公司/哪個業務的單？薪資欄位誰能看？這是 ABAC 的核心，不能只列名詞。 |
| **報表權限 / 資料匯出管控** | 🟡 | `bi` 服務無「誰能看哪張報表、哪些列、能不能匯出」的設計。財務報表外洩風險高。 |
| **資料保留 / 封存 / 法遵刪除** | 🟡 | 無資料生命週期策略（財務憑證在台須保存一定年限；個資則有刪除權）。 |
| **災難復原（DR）/ 備援** | 🟡 | Roadmap Phase 5 才出現「災備」，但 DB-per-service 會讓**備份/還原/時點一致性**指數級變難（19 個庫如何取一致快照？），應提前納入架構決策。 |
| **測試策略** | 🔴 | 現況**零測試**。財務系統至少要有：WAC 計算單元測試、借貸平衡性質測試（property-based）、Saga/補償的契約測試、關期前後試算表回歸。計畫的 North Star 寫「正確性」卻無測試章節。 |
| **編號產生的併發正確性** | 🟠 | `NextNumberAsync` 用 `Count(...) + 1`（行 306-313），**高併發會產生重複單號**（且作廢的單會讓 count 變小、再次重號）。拆服務後跨節點更糟。`mdm` 的編號規則應改為 DB sequence / Hi-Lo。 |
| **多倉的成本與庫存模型** | 🟡 | 現況 `Product.Stock`/`AvgCost` 是**商品層單一數字**，`StockMovement` 雖記 `WarehouseId` 但**庫存餘額不分倉**（扣庫只改 `Product.Stock`）。「多倉」其實尚未真正實作，計畫未點出。 |

## 5. 安全與合規

| 主題 | 計畫規劃 | 評斷 | 嚴重度 |
| --- | --- | --- | --- |
| 認證 | OIDC/OAuth2（Duende 或 Keycloak），閘道驗證 JWT | 方向正確。但「自建 IdentityServer」對小團隊是負擔；**建議直接用 Keycloak（或雲端 IdP）**，別自己維護身分服務。Duende 還需商業授權成本。 | 🟡 |
| 授權 | RBAC/ABAC，policy-based，各服務細粒度 | **只有名詞，無模型**。RBAC 的角色-權限-資源矩陣、ABAC 的屬性（公司/倉/部門/金額上限）來源與評估點都沒設計。**列級權限是 ERP 最常見的卡關點**，必須在 02/03 文件給出具體模型。 | 🟠 |
| 稽核不可竄改 | 「不可變稽核軌跡」「分錄不可刪僅可沖銷」 | 觀念對。但現況分錄**技術上可被刪/改**（無 append-only 約束、無雜湊鏈）。要落實「不可竄改」需：DB 權限收斂（應用帳號無 UPDATE/DELETE 分錄權）、或 append-only + 雜湊鏈/WORM 儲存。計畫沒講怎麼做。 | 🟠 |
| 財務期間鎖定 | cross-cutting 提「期間鎖定」 | **無機制**。現況 `Cancel*`/`ApplyAdjustment` 用 `DateTime.UtcNow` 直接寫過去/任意日期分錄，**完全不檢查期間是否已關**。這是合規硬傷，必須有「會計期間表 + 寫入時鎖定檢查」。 | 🔴 |
| 欄位級權限 | 「欄位級遮罩」 | 僅名詞。薪資、成本、客戶聯絡資訊等敏感欄位的遮罩策略需具體化（誰、在哪層遮罩、API 還是 UI）。 | 🟡 |
| 傳輸/輸入安全 | 提到傳輸/靜態加密、Secret 管理 | 合理。但現況 **CORS `AllowAnyOrigin` 全開**、無速率限制、無輸入驗證層（DTO 僅靠 `[Required]`）。轉型第一步就該收斂 CORS 與加上 FluentValidation。 | 🟠 |

**安全小結**：規劃「列了正確的清單，但幾乎都停在名詞層」。對財務/ERP 系統，**期間鎖定（🔴）與分錄不可竄改（🟠）必須有可驗證的機制**，不能靠約定。

## 6. 排序與可行性（Roadmap）

### 6.1 整體節奏評斷
「先治理骨幹（IAM/audit/workflow）→ 再核心流程 → 後擴充」的**大方向是對的**，這點值得肯定。但有數個相依性與時序問題：

### 6.2 相依性倒置 / 自相矛盾 🟠

| 問題 | 說明 |
| --- | --- |
| **ADR-01 與 Roadmap 矛盾** | ADR-01 寫「Strangler Fig，先重構為模組化單體**再逐一抽離**」；但 Phase 2 標題就是「拆既有單體」成 6 個服務、Phase 3「財務重構為事件驅動」。**中間「模組化單體」這一步在 Roadmap 裡消失了。** 應補一個明確的「Phase 1.5：單體內模組化（含補交易、補借貸 CHECK、補 audit 攔截器）」並在此**停留夠久**。 |
| **`mdm` 太晚** | 編號規則、幣別、稅率、共用代碼是**所有交易模組的前置**，卻排在 §3.2 第 19 位、實作散落。應**提前到地基/Phase 1**。 |
| **`workflow` 先於業務模組** | Phase 1 就上「可設定簽核引擎」，但此時**還沒有任何單據可簽核**。通用簽核引擎是出了名的難做且容易過度設計。建議**延後**，先在採購/請款上做**寫死的兩階簽核**，需求穩定後再抽象成引擎。 |
| **`bi`/資料倉儲與 `finance` 的時序** | BI 依賴各服務的讀取模型，但 Phase 4 才做 `bi`，而 Phase 3 的 finance 已事件化——中間**報表怎麼出**沒交代。模組化單體可直接查，問題消失（再次佐證別太早拆）。 |
| **資料遷移時點** | §7 寫「既有 InvenFlow 資料 ETL 匯入新服務」，但**舊資料量極小（demo）**，且新舊模型差異大（無稅、無公司）。與其做 ETL 工具，不如**直接以新模型重建 seed**，把 ETL 從計畫拿掉，省一個 Phase 5 工項。 |

### 6.3 應提前驗證的高風險 Spike（計畫完全沒有 spike 概念）🟠
建議在投入大規模實作前，先做這幾個一兩週的技術探針，證明風險可控再繼續：
1. **Spike A — 跨服務財務一致性**：用 2 個服務（inventory、finance）+ Outbox + 一個訊息匯流排，做出「出貨→COGS 入帳」的端到端，**故意注入重複/亂序/補償失敗**，看對帳能不能抓出來。若做不漂亮 → 證明「別拆 finance」。
2. **Spike B — 期間鎖定 + 沖銷**：實作會計期間表，驗證「關期後不能寫入該期分錄」「跨期作廢走當期沖銷」。
3. **Spike C — 多公司/多幣別的橫切改造成本**：在現有 12 張表上加 `CompanyId` + 原幣/本位幣，量測改動幅度，校準工時。
4. **Spike D — 稅務/發票**：把台灣統一發票（含折讓、字軌、401 申報欄位）模型化，驗證它對 Sale/Journal 的侵入程度。

## 7. 過度設計 / 維運風險

| 選擇 | 評斷 | 嚴重度 | 建議 |
| --- | --- | --- | --- |
| 一步到位 **19 個微服務** | 對 1–3 人團隊是壓垮性負擔 | 🔴 | 改模組化單體，見 §2 |
| **Kafka 升級路線** | 這個業務量（中小零售/分銷）**永遠用不到 Kafka 的吞吐**；RabbitMQ 都可能過早 | 🟠 | 先 in-process（Outbox 表 + 背景處理）；真要 broker 用 RabbitMQ 即上限，刪掉 Kafka |
| **Kubernetes + Helm** | 19 服務 × K8s 的維運/監控/網路/憑證複雜度，對小團隊是黑洞 | 🔴 | 起步用單機 / docker compose / 或 PaaS（App Service、Container Apps）。K8s 設「有 SRE 人力且服務數 > N」才啟用 |
| **gRPC（同步服務間）** | 單體內就是方法呼叫，不需要；微服務初期 REST 已足 | 🟡 | 移除 gRPC，需要時再評估 |
| **資料倉儲 / 列式 DB / OpenSearch（polyglot）** | demo 階段引入多種儲存，學習與維運成本高 | 🟠 | 全部用 SQL Server 起步，報表用讀取複本/物化檢視；搜尋需求出現再加 |
| **通用簽核引擎（workflow）** | 通用工作流引擎是經典過度設計來源 | 🟠 | 先硬編碼具體簽核，見 §6.2 |
| **自建 IdentityServer** | 自己維運身分服務的長期成本被低估（且 Duende 要授權費） | 🟡 | 直接用 Keycloak 或雲 IdP |
| **API Gateway（YARP）早於需求** | 單體不需要閘道 | 🟡 | 延後 |

**維運負擔總評**：計畫的技術選型**像是為「50 人工程組織 + 高流量 SaaS」設計的**，套在這個專案上，光是「讓 19 個服務在本機跑起來、CI 綠燈、可觀測性接好」就會吃掉絕大多數時間，真正的業務功能（稅務、退貨、定價）反而做不出來。**這是本計畫最大的務實風險。**

## 9. 必須修正（Must-fix）清單 🔴

1. **修正 As-Is 的關鍵誤述**：刪除/改寫「WAC 與分錄在單一 DB 交易完成」——實際**無交易保證**，這是既有 bug。背景、§2.2、ADR-03 一併更新。
2. **架構降級為「模組化單體優先」**：把 19 微服務改為「1 部署單元、6–8 個模組、預留拆分縫」。Kafka/K8s/gRPC/資料倉儲/YARP/Saga 全部移到「Phase 5 後、有量化觸發條件才啟用」。
3. **不要在 Phase 2/3 把會計分錄事件化**：`finance` 在單體內**同步同交易**產生分錄，沿用並補強 `AccountingService`（補顯式交易 + 借貸平衡 CHECK 約束）。
4. **新增「會計期間鎖定」機制**：會計期間表 + 寫入/沖銷時的關期檢查；禁止往已關期間寫分錄。
5. **新增稅務 / 統一發票 / 退貨折讓 為一級模組**：補進銷項稅額欄位與科目、發票字軌、紅字/折讓、退貨對庫存與 AR/AP 的處理。這是台灣 ERP 的營運底線。
6. **補測試策略章節**：至少 WAC 單元測試、借貸平衡 property test、關期回歸、（若日後拆）Saga 契約與對帳測試。
7. **修正編號併發 bug**：`mdm` 用 DB sequence / Hi-Lo 取代 `Count()+1`。
8. **補「跨服務一致性除錯與對帳」設計**（僅在確定要拆 finance 時）：冪等鍵、事件版本/排序、dead-letter、每日強制對帳、關期前置檢查。

1. **合併過細邊界**：`product`+`inventory` 合一；`crm` 併入 `sales`（或延後）；客戶/供應商主檔歸 `mdm`。
2. **`mdm` 提前**到地基/Phase 1（編號、幣別、稅率、共用代碼是所有交易前置）。
3. **GL 加維度（dimension）**：部門/成本中心/專案/據點，否則出不了部門損益與專案成本（與計畫的 mfg/project 目標相依）。

5. **稽核改為同源攔截器**：EF `SaveChanges` 攔截 + 同庫稽核表起步，別一開始做成異步消費的獨立服務（避免稽核遺失）。

7. **收斂 CORS**、加速率限制與輸入驗證（FluentValidation）。
8. **身分用 Keycloak/雲 IdP**，不自建 IdentityServer。
9. **補多倉庫存模型**：庫存餘額/成本需分倉（現況只在商品層），計畫應明確指出此為待補。

## 12. 給後續三份設計文件的具體指引

### 12.1 給 `02-資料庫設計.md`
- **以「模組 schema」而非「服務獨立 DB」為單位**：同一個 SQL Server/PostgreSQL 內用 schema（`iam.`、`inv.`、`fin.`…）隔離，禁止跨 schema FK 到他人核心表；保留日後拆庫的縫。
- **每張交易/主檔表加共用欄位**：`CompanyId`、`CreatedBy/At`、`UpdatedBy/At`、`RowVersion`（樂觀鎖）；交易表加 `CurrencyCode`、原幣/本位幣金額。
- **分錄表加硬約束**：`JournalLine` 借貸平衡可用「每筆 Entry 的 Σ(Debit)=Σ(Credit)」的應用層+觸發器/CHECK 雙保險；分錄表設**應用帳號無 UPDATE/DELETE 權**（只能 append + 沖銷）。
- **新增表**：會計期間（`AccountingPeriod`，含狀態 Open/Closed/Locked）、稅率與發票（`TaxCode`、`Invoice`/`InvoiceLine`、字軌 `InvoiceTrack`）、退貨/折讓（`SalesReturn`/`CreditNote`）、編號規則（`NumberSequence`）、稽核（`AuditLog`）、Outbox（即使單體也先建，欄位含 `EventId` 冪等鍵）、GL 維度（`Dimension`/`DimensionValue` 並掛到 `JournalLine`）。
- **多倉**：把庫存餘額與成本從 `Product` 拆到 `StockBalance(ProductId, WarehouseId, Qty, AvgCost)`，修正現況「庫存只在商品層」的問題。
- **既有資料對應**：以「重建 seed」為主、ETL 為輔；附「舊 12 表 → 新模型」對應表，並標出新欄位（稅、公司、幣別）的預設值策略。
- **WAC/批號政策決策表**：明確寫「採平均成本」時批號只做追溯不做批次成本；若要批次成本，另立政策。

### 12.2 給 `03-後端微服務設計.md`（建議改名為「後端模組化設計」）
- **第一章先定形態**：模組化單體 + 模組邊界 + in-process 介面（`IInventoryService`）+ in-process 事件（MediatR）+ Outbox 表；附「何時、依什麼量化指標才拆成獨立服務」的決策準則。
- **把財務一致性寫成兩套**：
  - **預設（單體）**：`sales`/`procure` 在**同一交易**呼叫 `finance` 產生分錄；給出交易邊界與失敗回滾範例（修正現況雙 SaveChanges）。
  - **未來（拆分後）**：才談 Outbox+Saga，且**必須**含：冪等（`EventId` 去重表）、事件版本/排序、補償失敗的人工佇列、**每日對帳作業**（庫存↔GL、AR/AP↔GL）、**關期前置檢查**。把這四件事當作驗收條件。
- **授權模型具體化**：RBAC（角色-權限-資源矩陣）+ ABAC（屬性：公司/倉/部門/金額上限）；定義**授權評估點**（中介軟體 + 資源層 filter）與**列級過濾**實作（如全域 query filter 依使用者可見公司/倉）。
- **期間鎖定服務**：所有寫分錄路徑（含 Cancel/Adjustment）統一經過「期間開放檢查」。
- **編號服務**：DB sequence/Hi-Lo，定義各單據字軌規則。
- **稽核**：EF SaveChanges 攔截器寫 `AuditLog`，定義不可竄改策略。
- **API 契約**：維持 OpenAPI→TS client（ADR-06）；給出錯誤模型（ProblemDetails）、分頁、冪等鍵 header 規範。
- **加 Spike 章節**：把 §6.3 的 A/B/C/D 列為設計前置實驗與其驗收標準。

### 12.3 給 `04-前端UIUX設計.md`
- **技術定案**：React 18 + TS + Vite + **Ant Design** + react-hook-form + zod + TanStack Query + Zustand + ECharts；OpenAPI 產生型別與 client（不手寫型別）。
- **權限驅動 UI 的具體機制**：以 IAM 回傳的權限集合驅動「選單可見性 / 按鈕 enable / 欄位遮罩」；**前端遮罩只是體驗，真正權限在後端 enforce**（明確寫出這條原則，避免把欄位級權限只做在前端）。
- **資訊架構**：以三大流程（O2C/P2P/Plan-to-Produce）組織導覽，而非以 19 服務羅列；先交付 `iam`、主檔（mdm/product/customer/supplier）、採購、銷售、庫存、財務（含試算表/AR/AP）這幾個畫面。
- **ERP 重表格表單的關鍵畫面規範**：列表（伺服器端分頁/篩選/欄位自訂/匯出權限）、主從單據（單頭+多明細的可編輯表格，含稅額即時計算列）、過帳/作廢/沖銷的二次確認與權限、發票/退貨折讓畫面。
- **財務正確性的 UI 呈現**：銷售/採購單即時顯示稅額、毛利、WAC 成本；試算表頁面顯示借貸合計與「是否平衡」紅綠燈；關期狀態在記帳畫面明示（已關期間禁止輸入）。
- **跨切面**：i18n（zh-TW 先行、文字外部化）、深色模式、錯誤/載入/空狀態、表單樂觀鎖衝突提示（對應 `RowVersion`）。
- **不要為尚未存在的模組（mfg/hr/payroll）先畫高保真畫面**，避免規劃先於需求。
